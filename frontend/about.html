What is AdminZero?

The Autonomous AI Privacy & Data Security Gateway engineered to render SQL injections, prompt manipulation, and database exfiltration mathematically impossible.

01 // The Core Problem

Traditional WAFs Are Dead in the Age of AI

Modern enterprise applications, autonomous AI agents, and Natural Language Interfaces now write their own SQL queries and API requests on the fly.

Legacy Web Application Firewalls (Cloudflare, AWS WAF, ModSecurity) rely on Regular Expressions (Regex) and known signature blacklists. In an AI world, attackers can bypass regex in seconds using inline comments (/**/), hex encodings, recursive nesting, and semantic prompt injections.

❌ Traditional Regex Firewalls
  • Pattern-based string matching easily bypassed
  • Zero understanding of SQL grammatical intent
  • Blind to AST recursion and nested subqueries
  • High rate of false positives on legitimate queries
✓ AdminZero 12-Layer AST Gateway
  • Parses raw strings into a strict Mathematical AST tree
  • Enforces semantic table and schema whitelist locks
  • Extracts AST intent and reconstructs queries safely
  • In-memory behavioral anomaly detection and PII scrubbing

⚡ Phase I: Ingress Traffic & Lexical Hygiene (L1 – L4)
Pre-Compilation Guard
LAYER 01 DIFFICULTY: EASY (RATE CAP)
L1: Rate Limiter — Dynamic Sliding Window Anti-Flood
Domain: Network & Traffic Hygiene · Max 30 req/min per IP

Maintains an in-memory sliding token bucket per client IP with full reverse-proxy awareness (trusts canonical X-Forwarded-For headers from Render, Cloudflare, and AWS). It blocks brute-force dictionaries, automated fuzzers (wfuzz, ffuf), and distributed denial-of-service query floods before any CPU-heavy parser logic executes.

🛑 Quenched Attack Vectors
  • Automated tool sweeps (sqlmap --batch)
  • Rapid fuzzing loops (>100 requests in seconds)
  • Denial-of-Service resource exhaustion
⚡ Intercept Signature
POST /v1/ctf/query [200 req in 5s]
--> 429 Too Many Requests
{ "blocked": true, "reason": "LAYER_1_RATE_LIMIT" }

Why Regex Firewalls Fail: Conventional WAFs often use static IP tables easily fooled by forged Client-IP headers. AdminZero verifies trusted edge proxy chains with timing-safe bucket consumption.

LAYER 02 DIFFICULTY: MODERATE
L2: Encoding Detect — Multi-Byte & Functional Obfuscation Guard
Domain: Lexical Representation Sanitization · Zero-Tolerance Unpacking

Inspects the raw and normalized query representations for obfuscation vectors. Detects Hex literals (0x...), double URL encodings (%2527), Unicode escapes (\uXXXX), hex escapes (\xXX), null bytes (\x00), ASCII/CHAR conversion functions (CHAR(), NCHAR(), ASCII()), binary representations (0b...), and SQLite hex string literals (x'4144...').

🛑 Quenched Attack Vectors
  • Hex-encoded table targets: SELECT * FROM 0x666c6167
  • Function wrappers: SELECT CHAR(102)||CHAR(108)...
  • Double-encoded SQL quotes: %2527%2520OR%25201%253D1
  • Null-byte injection string terminators
⚡ Intercept Signature
SELECT name FROM users WHERE name = CHAR(65,100,109,105,110);
--> 400 Bad Request
{ "blocked": true, "reason": "LAYER_2_ENCODING: CHAR_FUNCTION" }

Why Regex Firewalls Fail: Most WAFs run only one URL-decode pass. Attackers nest encodings (e.g. hex inside base64 inside url-encode) to fly directly under the radar. AdminZero scans for the actual encoding primitives.

LAYER 03 DIFFICULTY: MODERATE
L3: Keyword Blacklist — Destructive DDL & Side-Channel Shield
Domain: Signature & Primitive Filtering · Prohibits Mutative & Timing Primitives

Acts as a hard rejection gate for destructive SQL verbs (DROP, DELETE, TRUNCATE, ALTER), OS execution commands (xp_cmdshell, LOAD_FILE, OUTFILE), timing side-channels (SLEEP, BENCHMARK, pg_sleep, RANDOMBLOB), SQLite engine pragmas (PRAGMA, ATTACH, DETACH, VACUUM), multi-statement stack delimiters (;), and modern LLM prompt injections (ignore previous instructions, DAN mode).

🛑 Quenched Attack Vectors
  • Table destruction: '; DROP TABLE users;--
  • Blind timing extraction: ' OR RANDOMBLOB(500000000)--
  • SQLite database hijacking: '; ATTACH DATABASE ...
  • LLM prompt poisoning: ' UNION SELECT 'system: admin'
⚡ Intercept Signature
SELECT id FROM users; PRAGMA database_list;
--> 403 Forbidden
{ "blocked": true, "reason": "LAYER_3_BLACKLIST: /PRAGMA/i" }
LAYER 04 DIFFICULTY: MODERATE
L4: Query Normalizer — Zero-Width Stripper & Homoglyph Translator
Domain: Character & Whitespace Canonicalization · Strips Smuggled Tokens

Pre-processes incoming strings before grammar compilation. Strips zero-width unicode splitters (\u200B, \uFEFF) commonly placed inside keywords to evade regex filters, maps Cyrillic/Greek homoglyphs (e.g. Cyrillic а, е, о to ASCII a, e, o), collapses non-standard whitespace variants into single ASCII spaces, and enforces a strict 500-character payload length cap.

🛑 Quenched Attack Vectors
  • Keyword splitting: S\u200BE\u200BL\u200BE\u200BC\u200BT
  • Cyrillic visual lookalikes: ЅЕLЕСТ
  • Whitespace comment smuggling: SELECT/**/name/**/FROM/**/users
  • Buffer memory stuffing attacks (>500 chars)
⚡ Intercept Signature
SELECT\u200B*\u200BFROM\u200Busers
--> Canonicalized to: SELECT * FROM users
(Bypasses are stripped before compilation)
🧠 Phase II: Mathematical AST Compilation & Structural Analysis (L5 – L6)
Syntax & Complexity Engine
LAYER 05 DIFFICULTY: HIGH ★★★★☆
L5: AST Parser — Mathematical Grammar Verification
Domain: Grammar & Syntactic Analysis · Strict SQLite AST Compilation

Compiles the normalized SQL string into an Abstract Syntax Tree (AST) using an in-memory SQL grammar parser. If the query breaks SQLite grammar (such as unbalanced single quotes, broken logic fragments, or trailing syntax artifacts) or contains stacked multi-statement queries, compilation fails and the request is quenched immediately.

🛑 Quenched Attack Vectors
  • Quote-break boolean injections: ' OR '1'='1
  • Unterminated string syntax: admin' OR 1=1 --
  • Stacked semicolon injections: SELECT 1; SELECT 2
  • Grammar corruption payloads designed to force database leaks
⚡ Intercept Signature
' OR '1'='1
--> 403 Forbidden
{ "blocked": true, "reason": "LAYER_5_PARSE_FAIL: Invalid SQL syntax" }

Why Regex Firewalls Fail: Regular expressions guess whether a quote is suspicious. AdminZero evaluates SQL like a programming language compiler: if the string does not form a well-formed mathematical AST tree, it never reaches execution.

LAYER 06 DIFFICULTY: HIGH ★★★★☆
L6: Complexity Scorer — AST Depth & Cartesian Product Trap
Domain: Algorithmic Complexity & ReDoS Defense · Tree Depth ≤ 8, Nodes ≤ 40

Recursively walks the compiled AST to compute structural complexity metrics in O(N). Rejects any query whose AST exceeds 40 total nodes, a nesting depth greater than 8 levels, or a fan-out branching factor greater than 12 children per node. Defends against AST parser exhaustion, ReDoS, and combinatorial Cartesian product denial-of-service.

🛑 Quenched Attack Vectors
  • Deeply nested parentheses: ((((((((id=1))))))))
  • Exponential predicate chains designed to crash the query planner
  • Combinatorial Cartesian join explosions
  • AST parser recursion stack overflow exploits
⚡ Intercept Signature
SELECT id FROM users WHERE (((((((((((id = 1)))))))))));
--> 403 Forbidden
{ "blocked": true, "reason": "LAYER_4_COMPLEXITY: Depth limit exceeded" }
🛡 Phase III: Semantic Intent & Query Reconstruction (L7 – L9)
Core Bastion
LAYER 07 DIFFICULTY: VERY HIGH ★★★★★
L7: Intent & Semantic — Closed-World Whitelist & Scope Guard
Domain: Semantic Access Control · Closed-World Table & Column Whitelist

Performs deep semantic inspection on every AST node. Operates on a strict closed-world access model: only SELECT statements are permitted. Only whitelisted public tables (users, products) can be queried. Any mention of metadata tables (sqlite_master, sqlite_sequence) or secrets (flag_table, fake_flags, audit_log) is rejected. Furthermore, subqueries, CTEs (WITH ... AS), set operations (UNION, INTERSECT, EXCEPT), and wildcard SELECT * projections are forbidden. A hard row cap (max 10) is also enforced.

🛑 Quenched Attack Vectors
  • Metadata enumeration: SELECT * FROM sqlite_master
  • Secret extraction: SELECT * FROM flag_table
  • UNION-based data stealing: UNION SELECT null, flag FROM flag_table
  • Subquery extraction: SELECT (SELECT flag FROM flag_table) FROM users
  • Wildcard database dumping: SELECT * FROM users
⚡ Intercept Signature
SELECT name FROM users WHERE id IN (SELECT id FROM flag_table);
--> 403 Forbidden
{ "blocked": true, "reason": "LAYER_6_SUBQUERY: Nested SELECT (subquery) is blocked" }

Why Regex Firewalls Fail: Regex blacklists try to block words like "password". If a developer names a table "admin_tokens", regex fails completely. AdminZero uses a CLOSED-WORLD whitelist: unknown tables or columns are physically non-existent to the query engine.

LAYER 08 DIFFICULTY: EXTREME ★★★★★
L8: Query Reconstructor — Safe AST Re-Synthesis & String Destruction
Domain: Input Decoupling & Safe Code Generation · Original String Wiped

The attacker's raw user query string is permanently destroyed! AdminZero takes exclusively the validated AST nodes and regenerates brand-new, canonical SQL using parser.sqlify(stmtNode, { database: 'SQLite' }). Any smuggled comments, whitespace tricks, parser desynchronization artifacts, or dialect discrepancies are wiped from existence before the SQLite driver executes the query. The reconstructed query is then subjected to a secondary post-validation blacklist scan.

🛑 Quenched Attack Vectors
  • Parser desynchronization (exploiting differences between parser & engine)
  • Comment smuggling payloads: SELECT/*foo*/id FROM users
  • Driver-specific string interpolation exploits
  • Multi-byte smuggling where raw bytes bypass string filters
⚡ Architectural Proof
Input:  SELECT `id`, `name` FROM `users` WHERE `id`=1 /*smuggled*/
Output: SELECT `id`, `name` FROM `users` WHERE `id` = 1
--> The raw input string was completely discarded.
Only the AST-reconstructed query hits the DB engine.
LAYER 09 DIFFICULTY: VERY HIGH ★★★★★
L9: Shannon Entropy & Tokenizer — Zero-Trust Lexical Token Auditor
Domain: Lexical Entropy & Independent Parser Verification · Zero Trust in AST

A hand-rolled, zero-dependency lexical tokenizer operates directly on the raw string and the reconstructed string completely independent of node-sql-parser. It scans every token identifier and verifies that forbidden names (flag_table, flag, secret, audit_log, sqlite_master) do not appear anywhere in the query, neutralizing any theoretical zero-day AST parser categorization bugs.

🛑 Quenched Attack Vectors
  • Parser categorization zero-days (where a parser fails to identify a table token)
  • Bracketed and backtick identifier smuggling: [flag_table], `flag_table`
  • High-entropy obfuscated shell fragments
  • Dual-parser discrepancy attacks
⚡ Intercept Signature
SELECT id FROM users WHERE name = "flag_table";
--> 403 Forbidden
{ "blocked": true, "reason": "LAYER_9_TOKENIZER: Raw identifier 'flag_table' is forbidden" }
🎭 Phase IV: Deception, Anti-Automation & Egress Redaction (L10 – L12)
Active Defense & Privacy
LAYER 10 DIFFICULTY: CRUEL & DECEPTIVE ★★★★★
L10: Honey Canary & Behavioral Guard — Tiered Quarantine & Shadow Ban
Domain: Client Reputation & Deception Technology · 4 Escalating Penalty Tiers

Continuously scores each client IP across an escalating 4-tier behavioral penalty system:
• Tier 0 (0-2 blocks): Normal rejection responses.
• Tier 1 (3-5 blocks): Injects artificial delays (up to 2000ms jitter) + vague responses to slow automated fuzzers.
• Tier 2 (6-9 blocks): SHADOW BAN — Returns HTTP 200 OK with plausible FAKE decoy data (e.g. decoy users like "Ravi Issak" and fake product records) so attackers waste hours analyzing fabricated honey canary data.
• Tier 3 (10+ blocks): Hard ban quarantining the IP with HTTP 403.

🛑 Quenched Attack Vectors
  • Automated payload discovery loops
  • Blind SQL injection timing measurements (ruined by random jitter)
  • Adversarial reconnaissance (hackers waste time analyzing fake honey data)
  • Persistent botnet probes
⚡ Shadow Ban Honeypot
POST /v1/ctf/query [after 6 failed attempts]
--> 200 OK
{ "rows": [{ "name": "Ravi Issak", "role": "admin" }] }
(Attacker thinks they succeeded, but data is 100% fabricated decoy!)
LAYER 11 DIFFICULTY: VERY HIGH ★★★★★
L11: Challenge Token Chaining — HMAC-SHA256 Anti-Automation Rotation
Domain: Cryptographic State & Session Verification · Sequential Execution Enforced

Every response signs an HMAC-SHA256 cryptographic challenge token (X-Next-Token) bound to the client's IP, request ID, and timestamp window. Subsequent requests must present this token in the X-Challenge-Token header. This enforces strictly sequential query execution, neutralizing parallel burst attacks, asynchronous replay bots, and headless fuzzers.

🛑 Quenched Attack Vectors
  • Parallelized multi-threaded fuzzing (Burp Intruder at 100 threads)
  • Headless replay scripts lacking state handlers
  • Race-condition concurrency attacks
  • Distributed request amplification
⚡ Intercept Signature
POST /v1/ctf/query [without valid X-Challenge-Token]
--> 403 Forbidden
{ "blocked": true, "reason": "LAYER_11_CHALLENGE_FAILED" }
LAYER 12 DIFFICULTY: FINAL WALL ★★★★★
L12: PII Scrubber & Output Redactor — In-Memory Egress Sanitization
Domain: Data Exfiltration & Privacy Defense · Zero Leaks on Egress

The final barrier before data leaves the server. Intercepts raw database result rows in memory and applies dynamic PII redaction: masks email addresses (e.g. r***k@glitchgo.tech), masks phone numbers, replaces passwords, hashes, tokens, API keys, and secret values with ***REDACTED***, and caps results to a maximum of 10 rows to prevent full-table exfiltration.

🛑 Quenched Attack Vectors
  • Bulk database table dumping
  • Credential theft through leaked user records
  • PII harvesting (emails, phone numbers, addresses)
  • Side-channel flag leakage in non-flag tables
⚡ Intercept Signature
SELECT id, name, email, role FROM users LIMIT 100;
--> Capped to 10 rows; email masked in-memory to:
{ "name": "Issak", "email": "i***k@glitchgo.tech", "role": "admin" }

Why Regex Firewalls Fail: WAFs only inspect INPUT. If an application leaks sensitive data in the database response, a traditional WAF does nothing. AdminZero guards both ingress and egress: even if an unexpected row is read, Layer 12 sanitizes the output in memory before serialization.
